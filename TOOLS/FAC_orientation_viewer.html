F.A.C. Orientation Viewer

Reads the 27-byte telemetry packet of a F.A.C. V2 board over USB and draws its orientation in 3D. It is a diagnostic tool: nothing is ever written to the board except the telemetry request byte.

Connecting

Needs the Web Serial API — Chrome, Edge or Opera on desktop. Firefox and Safari do not implement it. Click Connect and pick the F.A.C. virtual COM port. The tool then sends command byte 4 (FAC_USB_COMMAND_TELEMETRY_REQUEST) at the selected rate and decodes the reply. Demo runs the whole interface off a synthetic tumbling board, with no hardware attached.

What is real and what is not

Only roll and pitch are measured. The telemetry packet carries the accelerometer and nothing else — no gyroscope. A stationary accelerometer reads the direction of gravity, which fixes two attitude degrees of freedom out of three. Yaw is unobservable from gravity (rotating about the vertical does not change the reading by one count) and this board has no magnetometer.

So the model's heading is a convention, not a measurement: the tool freezes it exactly the way the firmware does, by projecting body +X onto the horizontal plane. Rotate the real board flat on a table and the model will not turn. That is correct behaviour, not a bug.

A second consequence worth remembering: the accelerometer measures specific force, not gravity. While the robot is being shaken, thrown or hit, the vector it reports is not vertical and the orientation shown is meaningless. Read it on a robot standing still.

The sign check — and what it really costs

The firmware takes up = normalize(accel_mean) without negating it, on the standard MEMS convention that the axis pointing upwards reads +1 g at rest. Put the board flat with the components facing up: Z should read about +1000 mg. If it reads −1000, negate the vector in FAC_IMU_BUILD_frame() in fac_imu.c.

Most of what you would expect to break, does not — and it is worth knowing why before going hunting for a bug that is not there. If the sensor reported −s instead of s, the calibration would store up = −u, and the projection afterwards would give (−u)·(−s) = u·s. The sign appears twice on the accelerometer path and cancels. forward is invariant too, because the projection term (X·up)·up contains up twice. Only up and left come out negated, which is the same frame rotated 180° about forward: a world with X forward, Y right and Z down.

Unaffected: tilt angle, is_upside_down, levelled accel Y and Z, levelled gyro X (pitch rate).

Inverted: levelled accel X (forward), levelled gyro Y (roll rate), and — the one that matters — levelled gyro Z, so FAC_IMU_GET_yaw_rate_mdps() and the integrated heading run backwards.

The reason the gyroscope is the one that suffers: an accelerometer sign convention does not negate the gyroscope, so there is no second sign to cancel against, and the flipped axes go straight through. It is also why this cannot be detected automatically — a board at rest reading (0, 0, +1000) is indistinguishable from an upside-down board under the opposite convention. The answer comes from the datasheet, not from the data.

Calibration preview

The firmware calibrates the IMU when the robot is armed, not at boot, and refuses the measurement unless the robot is genuinely still. This panel runs the same three checks live so you can see whether a calibration would pass before you try to arm:

  • Magnitude between 800 and 1200 mg — the board is standing on a floor and not being accelerated. In the firmware this is IMU_CALIBRATION_ACCEL_MIN/MAX, expressed there in raw counts (1639…2459).
  • Span under 49 mg — IMU_CALIBRATION_MAX_ACCEL_SPAN, 100 counts. Indicative only: the firmware measures it over 128 samples at 416 Hz inside a 400 ms window, while this tool can only see the polling rate you selected. Treat it as a rough "is it moving" indicator, not as the firmware's own verdict.
  • Per axis limit under 4 g — IMU_CALIBRATION_ACCEL_LIMIT. This one is not a taste threshold, it is the overflow guard of the sum of the squares.

The gyroscope span check the firmware also runs cannot be previewed here: the gyro is not in the telemetry packet.

Capture reference freezes the current attitude as the calibrated frame, exactly as arming would, and then shows the levelled vector, the tilt relative to that pose and the is_upside_down flag. It is the way to check on the bench what a mix will actually read once the robot is armed in that position.
